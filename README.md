# Кандидатогенерация для поиска услуг Авито

Задача: по поисковому запросу выбрать до 50 объявлений из корпуса в 189 212 объявлений так, чтобы среди них оказалось
то, которое пользователь в итоге выбрал. Метрика — Recall@50.

**Мой результат на платформе: 0,8998** (на Stepik отображается как 0,9).

## С чего я начал: что показали данные

Прежде чем строить модель, я посмотрел на данные (`eda.ipynb`), и несколько цифр сразу определили архитектуру:

* **Train почти не пересекается с корпусом бенчмарка.** Выбранное объявление из train лежит в корпусе только в 6,6% строк.
  Значит, запомнить «запрос → объявление» не получится. Train я использую для статистик, валидации и обучения моделей.
* **Бенчмарк — длинный хвост.** Дословно в train встречается 37,5% запросов, вместе с локацией — только 6,7%.
  Поэтому на историю можно опереться лишь для трети запросов, а основную работу должны делать текстовый и смысловой поиск.
* **География решает многое.** 83% выборов — объявления из той же локации, что и поиск, медианное расстояние 2,9 км.
  При этом у 17% запросов в их локации нет ни одного объявления: обычно это поиск по региону.

## Решение

### Кандидаты

Для каждого запроса я собираю пул примерно из 600 кандидатов из нескольких независимых каналов:

* **BM25 по леммам**: топ-300 в «гео-множестве» запроса и топ-100 по всему корпусу. Гео-множество — это своя локация плюс
  локации, куда, судя по train, уходят выборы при поиске из неё. Для регионов без своих объявлений оно указывает на ближайшие
  города. Одна эта мера подняла BM25 с 0,37 до 0,82.
* **Эмбеддинги**: `multilingual-e5-base` и `USER-bge-m3`, которую я дообучил на 200 тыс. парах «запрос → выбранное объявление»
  из train. Они находят объявления без общих слов с запросом.
* **История похожих запросов** из train: какие объявления и микрокатегории выбирали по похожим запросам.

### Ранжирование

Пул сначала упорядочивает ручная формула: BM25, Reciprocal Rank Fusion по рангам каналов, косинус дообученной модели,
вероятность локации и совпадение фильтра. Веса я подобрал покоординатным спуском на валидации.

Затем ансамбль из двух CatBoostRanker (YetiRank, 47 признаков) переупорядочивает топ-200 формулы, а итоговый скор —
смесь скоров CatBoost и формулы.

Больше всего дали признаки, которые описывают, как пользователь выбирает на самом деле:

* расстояние до центра локации поиска;
* совпадение запроса с заголовком (пользователь смотрит прежде всего на него);
* BM25 отдельно по параметрам и описанию;
* вид и тип услуги объявления: совпадение с фильтром запроса и частота по похожим запросам;
* плюс ранги и скоры всех каналов.

## Как я проверял качество

Попыток на платформе всего 7, поэтому все решения я принимал по локальной валидации (`solution.ipynb`, разделы 5 и 7):

* беру 3000 поисков из train, у которых выбранное объявление есть в `benchmark_items`, и ищу по всему корпусу бенчмарка —
  тогда у правильного ответа те же конкуренты, что и на платформе;
* подбираю длину запросов и долю фильтров как в бенчмарке;
* убираю из истории пары «запрос + локация» из валидации и сами объявления-ответы;
* recall знакомых и новых запросов взвешиваю в пропорции бенчмарка (37,5% / 62,5%).

| № | Что добавил | Локально | Платформа |
|---|---|---|---|
| 1 | BM25 + гео + история | 0,847 (оптимистичная) | 0,7925 |
| 2 | + e5-base, пессимистичная валидация | 0,869 | 0,8545 |
| 3 | + дообученная USER-bge-m3 | 0,906 | 0,8912 |
| 4 | + CatBoostRanker в смеси с формулой | 0,912 | 0,8923 |
| 5 | + новые признаки, 6000 обучающих запросов, 2 модели | 0,921 | **0,8998** |
| 6 | 3 модели, CatBoost без формулы | 0,918 | 0,8915 |

После исправлений валидации локальная оценка выше платформенной на 1,4–2 п.п. и меняется в ту же сторону, поэтому ей
можно доверять при выборе улучшений. Финальная версия — шаг 5.

## Ошибки, которые я нашёл, и что с ними сделал

* **Утечка через историю объявлений.** Первая отправка дала 0,7925 при локальной оценке 0,847 — разрыв около 5 п.п.
  Оказалось, что у ответов валидации история в train есть всегда, а у ~90% объявлений бенчмарка её нет.
  Я убрал ответы валидации из истории, и после этого лучший вес канала истории объявлений стал 0.
* **Смещение в сторону знакомых запросов.** В валидации их было 77%, в бенчмарке — 37,5%. Теперь recall считается
  с весами бенчмарка.
* **Утечка в CatBoost через отбор строк.** Первая версия ранжировщика дала Recall@50 = 0,05 — хуже случайного.
  В обучение попадал топ-200 формулы плюс правильные ответы ниже топа, и модель выучила правило «плохой ранг = правильный
  ответ». Заметил по двум признакам: самым важным признаком был ранг формулы, а качество — хуже случайного.
  Исправил так: обучение и переранжирование идут на одном и том же топ-200.
* **Шум валидации.** Стандартная ошибка на 3000 запросах — около ±0,5 п.п., поэтому приросты меньше ~1 п.п. я не считал
  доказанными. Например, первая версия CatBoost дала +0,7 п.п. локально и только +0,1 на платформе.
* **Чистый CatBoost хуже смеси.** Без формулы на платформе вышло 0,8915 против 0,8998 у смеси. Формула не подстраивается
  под обучающую выборку и страхует ранжировщик.

## Что бы я улучшил

* Дообучение эмбеддингов: маскировать ложные негативы, брать «трудные» негативы из близких микрокатегорий, учить дольше
  (loss к концу эпохи ещё снижался).
* Валидацию побольше и абляции признаков ранжировщика — на них у меня не хватило времени.

## Структура репозитория

| Файл | Что это |
|---|---|
| `eda.ipynb` | исследование данных |
| `solution.ipynb` | полное решение: от данных до `answer.csv` |
| `answer.csv` | ответ, отправленный на платформу (Recall@50 = 0,8998) |
| `models/` | две модели CatBoostRanker, построившие отправленный ответ |
| `check_submission.py` | проверка формата `answer.csv` |
| `requirements.txt` | зависимости |

## Как запустить

1. `pip install -r requirements.txt`.
2. Выполните `solution.ipynb` сверху вниз. В разделе 1 недостающие файлы (данные задания и готовые артефакты) сами
   скачиваются с Google Drive в `data/` и `data/work/`; то, что уже лежит на диске, не скачивается. Путь к данным можно
   задать в `AVITO_DATA_DIR`. Результат — `data/work/answer.csv`.
3. Проверьте формат: `python check_submission.py data/work/answer.csv data/`.

Если хотите дообучить bge-m3 сами, а не брать готовую модель из раздела «Готовые артефакты», выполните приложение A
в `solution.ipynb` (`RUN_FINETUNE = True`, нужен GPU).

Без готовых артефактов эмбеддинги корпуса считаются ~40 мин на T4. Остальное работает на CPU: полный прогон занимает ~2 ч,
на GPU с готовыми кэшами — ~30 мин.

## Воспроизводимость

Всё, кроме шагов на GPU, детерминировано: фиксированные seed у валидации и выборок, BM25, история, признаки, формула.
Чтобы получить ровно отправленный `answer.csv`:

* модели CatBoost лежат в `models/`. При `USE_SAVED_RANKERS = True` (раздел 15) ноутбук загружает их вместо обучения:
  сначала из `models/`, затем из `data/work/`. Если файлов нет, модели обучаются заново, и результат может немного
  отличаться: при повторном обучении на валидации у меня было 0,917 вместо 0,920;
* дообученную bge-m3 нужно взять из готовых артефактов;
* в конце раздела 16 собранный ответ сверяется с `answer.csv` из корня репозитория.
